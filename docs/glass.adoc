= Glass decorations
:toc:

This page documents the additions this fork makes on top of upstream AeroSpace.
Everything here is inert unless you turn it on, so an upstream config keeps working unchanged.

== The tabbed layout

`tabbed` is a third tiling layout beside `tiles` and `accordion`.
Every window in the container gets the same rect, minus a strip reserved at the top for the tab bar,
so only the most recently used window is visible and the others sit behind it.

[source,bash]
----
aerospace layout tabbed          # tab up the focused window
aerospace layout tiles tabbed    # toggle between tiles and tabbed
----

Unlike the other layouts, `tabbed` scopes to the *focused window* rather than retiling its whole
parent: tabbing up a window in the corner of the screen puts a tab bar over that tile, it doesn't
swallow the entire workspace. The window is wrapped in a new tabbed container holding just itself,
showing a single tab.

Windows are then moved in and out with the ordinary `move` command — moving a window into a tabbed
container adds it as another tab instead of descending into whatever the visible tab holds:

[source,bash]
----
aerospace move left     # from the tile beside it: becomes a new tab
aerospace move right    # from inside the container: moves back out
----

A tab group is always horizontal, whatever orientation it was created with and whatever
`enable-normalization-opposite-orientation-for-nested-containers` would prefer. Its tabs run left to
right in the bar, so `focus left` and `focus right` step between them and then out of the group,
while `focus up`/`down` leave it directly. This is the same split i3 draws between its tabbed and
stacked layouts.

[source,bash]
----
aerospace focus left     # previous tab, then out of the group
aerospace focus right    # next tab, then out of the group
----

A tabbed container is exempt from `enable-normalization-flatten-containers`. Without that exemption
a container holding a single tab would be flattened away the instant it was created.

This is i3's tabbed layout.
Upstream maps i3's tabbed layout onto `h_accordion`, which keeps every window slightly offset so a
sliver of each neighbour peeks out; it never tells you the titles, and it is hard to see how many
windows are stacked. The tab bar answers both.

The bar is mouse-aware, and none of it activates AeroSpace or steals focus from your app: clicking a
tab focuses its window, hovering a tab reveals a close button at its left edge, and tabs can be
dragged — within the bar, into other tab groups, or into the layout. See <<drag-and-drop>>.

Orientation does not apply to `tabbed`, and `aerospace list-windows --format '%{window-layout}'`
reports `tabbed` regardless of the container's orientation.

The bar is drawn only while `glass.tabs.enabled` is true.
With it off, `tabbed` still works as a layout — it just stacks the windows with no visible chrome,
and the strip is not reserved.

Fullscreen hides the decorations rather than being floated over by them: a macOS-native fullscreen
app takes its own Space, which the panels deliberately don't join, and while an
aerospace-`fullscreen` window covers a workspace no bars or borders are drawn on its monitor.

[#drag-and-drop]
== Drag and drop

Dragging a tiled window by its title bar no longer merely swaps it with whatever sits underneath.
While the drag is in flight an overlay sketches the workspace's splits as faint outlines, and the
slot the drop would land in is filled with blurred glass. Where the window lands depends on where
over the target cell you release it:

* *Center of a tile* — the two windows swap places, as before.
* *Near an edge of a tile* — the dragged window splits that tile, taking the half you pointed at.
  If the tile's parent split already runs that way the window simply joins it at that position;
  otherwise the tile is wrapped in a new split, the same tree shapes the `move` command produces.
* *The tab bar strip of a tab group* — the window joins the group as a tab at the exact position
  the insertion caret shows.
* *The body of a tab group* — the window joins the group as its last tab.
* *The top edge of any tile* (a band one bar tall, wherever the tile sits on screen) — the window
  becomes a tab of that tile, creating the tab group on the spot when it doesn't have one yet. The
  preview marks the cell and sketches the bar the drop will grow across its top. The `up` split
  zone starts just below the band. Tiles too short to fit a bar don't offer the zone.
* *An edge of a tab group* — the group is split as a whole, tabs travelling together.
* *An empty workspace on another monitor* — the window becomes its first tile.

Dropping in a dead zone (your own cell, an empty stretch of desktop on the same workspace) cancels
the drag: the window snaps back to its slot. The tree is only mutated on mouse-up — during the drag
the layout stays put, so there is no live reshuffling to chase the cursor through.

Tabs in a glass tab bar are draggable too, and resolve against the same drop targets:

* *Within their own bar* — reorder; the caret shows the insertion point.
* *Onto another group's bar or body* — the tab moves to that group.
* *Onto a tile or its edges* — the tab leaves the group and swaps with or splits that tile.
* *Past the bar into nothing in particular* (about 40pt vertically) — the browser tear-off: the tab
  becomes its own tile right beside the group.

A tab that fronts a nested container moves as a whole, like its single tab suggests.

*Middle-drag* anywhere on a tab bar — tabs included — picks up the entire group and moves it as one
node through the same drop targets: split a tile with it, swap with one, send it to another
monitor, or drop it onto another group's bar to nest it there as a single tab. A plain middle-click
releases over the group's own cell, which is a dead zone, so it does nothing.

The preview is configured under `glass.drop-preview` (see <<configuration,Configuration>>); setting
`glass.drop-preview.enabled = false` disables the overlay while keeping the drop behavior.

== Window borders

An optional border drawn around each tiled window on a visible workspace, to show which one has
focus. Off by default, because it costs one overlay panel per visible window.

[source,toml]
----
glass.borders.enabled = true
----

Borders are never drawn for windows of invisible workspaces.
AeroSpace implements virtual workspaces by parking the windows of inactive workspaces in a screen
corner; a border tool that doesn't know about this — such as JankyBorders — draws for those parked
windows too, which is the well-known pile of stray borders in the corner of the screen.
Because this implementation reads AeroSpace's own tree, it simply doesn't draw them.

In a `tabbed` container only the visible window is given a border, since the others share its rect.

== Theming from the wallpaper

`glass.theme.from-wallpaper = true` takes the decoration colors from the desktop picture rather than
from the config.

The picture is decoded to a 96pt thumbnail and its colors bucketed into a coarse cube — wallpapers
are photographs, so no exact color repeats and counting them individually says nothing about which
tones the picture is made of. Five roles are then filled:

* *surface* — the most common tone darker than 22% luminance, which the tab bar strip uses. A
  picture with no dark region at all has its dominant tone darkened instead, so the bar still
  recedes rather than glowing.
* *elevated* — surface raised a step, for unselected tabs.
* *accent* — the tone scoring highest on saturation weighted by how much of the picture it covers,
  so a colour has to be both vivid and actually present to win. It marks focus: the selected tab,
  the border ring, the drop preview's outline. A greyscale wallpaper yields a light neutral rather
  than an invented hue.
* *onSurface* and *onAccent* — black or white, whichever stays legible on the surface it lands on.

Sampling is cached against the wallpaper's path and modification date, so it costs two `stat` calls
per refresh and re-runs only when the picture actually changes. When there is nothing to read — an
aerial video, an unreadable file — every configured color is used unchanged.

[#configuration]
== Configuration

All keys are optional. Sizes are whole points — TOML floats are not supported by AeroSpace's config
parser. Colors accept `+#RRGGBB+`, `+#RRGGBBAA+`, or JankyBorders-style `0xAARRGGBB`, so you can
paste a color straight out of an existing `borders` setup.

[source,toml]
----
# Sample every color below from the desktop picture. The palette owns the tints, the border
# colors and the preview accent while it is on; the keys that default to "derive it"
# (tabs.text-color, tabs.active-text-color, tabs.active-border-color) still win when set.
glass.theme.from-wallpaper = false

glass.borders.enabled =        false   # draw borders at all
glass.borders.width =          3       # total ring thickness; most of it is glass
# Of that width, the solid accent along the ring's outer edge. The rest stays tinted glass, so
# stroke-width = width gives a flat stroke and no glass shows at all.
glass.borders.stroke-width =   1
# Grow the layout gaps so two neighbouring windows' rings don't meet in the middle of the gap.
# Inner gaps gain twice the ring's outward reach, outer gaps gain it once.
glass.borders.expand-gaps =    true
# Ask the window server for each window's own corner radius. Windows genuinely differ — on
# macOS 26 a Safari window is 26pt where a VS Code window is 16pt — so one value can't fit all.
glass.borders.detect-corner-radius = true
glass.borders.corner-radius =  11      # fallback, used when detection is off or unavailable
# Per-app radius overrides by bundle id. These beat the detected radius, for windows whose
# reported corners don't suit their chrome.
# Find an app's id with:  aerospace list-windows --all --format '%{app-bundle-id} %{app-name}'
glass.borders.app-corner-radius = { 'com.apple.Terminal' = 11, 'org.alacritty' = 0 }
glass.borders.padding =        0       # outward offset; 0 hugs the window edge
glass.borders.show-inactive =  true    # also outline unfocused windows
glass.borders.active-color =   '#8CC7FF'
glass.borders.inactive-color = '#FFFFFF2E'

glass.tabs.enabled =       true
glass.tabs.height =        30          # height of the reserved strip
glass.tabs.padding =       0           # gap above the bar, between the top of the tile and the strip
glass.tabs.spacing =       4           # gap between the strip and the windows below
glass.tabs.corner-radius = 10
glass.tabs.font-size =     12
glass.tabs.show-icons =    true        # show each window's app icon in its tab

# The three fills form a value ramp: the strip is dim, unselected tabs sit a shade darker against
# it, and the selected tab is the lightest thing in the bar. Label colors are derived from whichever
# fill a tab uses, so text stays legible if you retune them.
glass.tabs.bar-tint =      '#00000038'
glass.tabs.inactive-tint = '#00000047'
glass.tabs.active-tint =   '#FFFFFF59'
# Label colors. Unset picks black or white from the fill's luminance, which suits most themes.
glass.tabs.text-color =          '#FFFFFFEB'   # unselected tabs
glass.tabs.active-text-color =   '#FFFFFFEB'   # the selected tab
glass.tabs.active-border-color = '#8CC7FF'     # hairline marking the selected tab

glass.drop-preview.enabled =       true
glass.drop-preview.corner-radius = 10
glass.drop-preview.tint =         '#8CC7FF21'  # faint fill of the active drop slot; the blur does the work
glass.drop-preview.stroke-color = '#8CC7FFE6'  # outline of the slot, and the tab insertion caret
glass.drop-preview.cell-color =   '#FFFFFF40'  # faint outlines sketching the other cells
----

== How it is drawn

The decorations are non-activating, borderless `NSPanel` overlays at the `.floating` window level,
reconciled at the end of every refresh session against the geometry the layout pass already cached
on the tree. No Accessibility API calls are made to place them, so they add no round-trips to the
layout hot path. Window titles and actual window frames are the exceptions: they come from the
Accessibility API asynchronously and are cached, so a stalled app can't stall the layout pass. A
tab shows the app name until its title arrives, and a border is drawn around the intended rect
until the real frame lands — some windows refuse the exact frame they are given (terminals snap to
their cell grid), and the border follows where the window actually ended up.

On macOS 26 the panels use Liquid Glass (`NSGlassEffectView` / SwiftUI `glassEffect`). On macOS 25
and earlier they fall back to `NSVisualEffectView` blur materials. Either way the blur is composited
by the window server, so it picks up the windows of other applications without the Screen Recording
permission.

One private symbol is touched, and only for `glass.borders.detect-corner-radius`:
`SLSWindowIteratorGetCornerRadii` reports a window's real corner radius, which is otherwise
unknowable — windows disagree, so a single configured radius leaves the ring floating around some
of them. It is resolved with `dlsym` at startup rather than linked, so a macOS release that removes
it degrades to `glass.borders.corner-radius` rather than breaking the app. Setting
`detect-corner-radius = false` avoids the symbol entirely.

Known limitations:

* Because the panels sit at the `.floating` level, a floating window placed over a tiled one is
  drawn *under* that window's border.
* Apple has an open regression (FB/forums thread 810314) where `NSGlassEffectView` in a borderless
  window can cache its backdrop and fail to refresh as windows move beneath it. If you hit it, the
  decorations still track window geometry correctly; only the blurred content behind them goes
  stale.

== i3-compatible split

Upstream's `split` refuses to run while `enable-normalization-flatten-containers` is on, which is
the default:

....
'split' has no effect when 'enable-normalization-flatten-containers' normalization enabled.
....

The complaint is real: that normalization dissolves any container holding a single child, so a
freshly split container would be flattened away before anything could join it.

This fork creates the container immediately anyway, the way i3 does, and marks it as deliberate so
the normalization leaves it alone while it holds a child. The split is therefore a real container
you can put windows into straight away:

[source,bash]
----
aerospace split vertical    # the focused window is now alone in a vertical container
aerospace move left         # from the tile beside it: stacks below, inside the split
----

New windows opening beside the split window land inside it too, since they are placed next to the
most recently used window and that window is now inside the container.

A container created by `split` also keeps the orientation you named, even when
`enable-normalization-opposite-orientation-for-nested-containers` is on. That normalization flips a
nested container to the opposite of its parent, which would make `split horizontal` inside a
horizontal parent silently mean vertical — the command would do the opposite of what it says.
Containers created any other way are still normalized as before.

Splitting from inside a tab divides the whole tab group rather than nesting a split within the
focused tab. Nesting would shrink only the visible tab and leave its siblings at the container's
full size. i3 reaches the group with `focus parent` first; AeroSpace has no equivalent, so the group
is split directly.

`join-with` is unchanged and is still the more direct way to put existing windows under a common
parent.
